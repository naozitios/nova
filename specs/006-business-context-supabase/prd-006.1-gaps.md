## Gap Analysis

### 1. PaddleOCR Worker (Critical)

**Current state**: Worker code exists (`workers/paddleocr/worker.py`), but:
- No Dockerfile
- No deployment config
- `paddlepaddle==2.6.1` no longer on PyPI (latest is 3.x with breaking changes)
- Worker only runs on `localhost:8000`

**Impact**: Any scanned PDF, image, or image-heavy document cannot be processed. The `DocumentParserRouter` correctly detects empty text and emits OCR warnings, but there's nothing to fall back to.

**Options**:
- A) Fix PaddleOCR: Update to PaddlePaddle 3.x, write Dockerfile, deploy to Cloud Run/K8s
- B) Use alternative: Google Vision AI, AWS Textract, or Azure Document Intelligence (all have OCR APIs)
- C) Defer: Mark scanned docs as "needs manual text input" in onboarding

**Recommendation**: Option B (Google Vision or AWS Textract) — simpler deployment, better accuracy, pay-per-use.

### 2. Extraction Quality (High)

**Current state**: Groq extracts 5 facts from 37-slide presentation:
```
1. business.name = "NOVI" (confidence: 1)
2. offers.primary = "Healthcare services" (confidence: 0.8)
3. customers.target_segment = "Individuals with diabetes..." (confidence: 0.7)
4. brand.tone = "Personal, authentic, and warm" (confidence: 0.9)
5. economics.ltv = null (confidence: 0)
```

**Problems**:
- Missing: pricing, team size, revenue, campaign metrics, content strategy, competitors, channels
- `economics.ltv` extracted as null (should be skipped or flagged)
- No source excerpts for most facts
- Fact key naming inconsistent (`business.name` vs `offers.primary`)

**Root cause**: System prompt too generic. Schema doesn't match actual content types (marketing campaigns, not business plans).

**Fix needed**:
- Purpose-specific extraction prompts (marketing context vs business plan vs financial report)
- Better schema design with required vs optional fact categories
- Source excerpt extraction (Groq returns `sourceExcerpt` but adapter doesn't persist it)
- Confidence calibration (null values should be filtered out)

### 3. API Route E2E Test (High)

**Current state**: Tested service layer directly. API routes have:
- Auth checks (`requireAuthz` with `X-User-Id` header in dev)
- Idempotency enforcement
- Input validation (Zod schemas)
- Error responses

**Not tested**: Whether a real HTTP request flows through all these layers correctly.

**Fix needed**: Write HTTP-level integration test using `fetch` against `npm run dev`.

### 4. Job Runner (High)

**Current state**: `JobRunner` class exists with polling, leasing, heartbeat, retry, dead-letter. But:
- Never instantiated in any startup code
- No `npm run dev` hook to start it
- Handlers are stubs (return metadata, don't actually process)

**Fix needed**: Wire job runner to Next.js startup or separate process.

## Remediation Plan

### Phase 1: Fix Extraction Quality (1-2 days)

1. **Create purpose-specific extraction prompts**
   - Marketing campaign content → extract: offers, channels, audiences, metrics, brand voice
   - Business plan → extract: revenue, team, market, competition, funding
   - Financial report → extract: revenue, growth, margins, projections

2. **Fix fact filtering**
   - Skip null/empty values
   - Validate confidence > 0 before persisting
   - Extract source excerpts from Groq output

3. **Add extraction test with real content**
   - Test with PPTX (marketing campaign)
   - Verify 15+ facts extracted with proper structure
   - Verify source excerpts preserved

### Phase 2: Fix API Routes (1 day)

1. **Write HTTP-level integration test**
   - Start `npm run dev`
   - POST to `/api/businesses/[id]/context/sources` with `X-User-Id`
   - Verify source created
   - POST to process endpoint
   - Verify job created

2. **Fix auth for local dev**
   - Ensure `X-User-Id` header works
   - Test with seed data user IDs

### Phase 3: Job Runner (1-2 days)

1. **Wire job runner to startup**
   - Add to `src/app/api/startup.ts` or separate worker process
   - Register extraction handlers
   - Start polling on dev server boot

2. **Test full async flow**
   - Register source → queue job → runner picks up → processes → saves facts

### Phase 4: OCR Alternative (2-3 days)

1. **Evaluate OCR options**
   - Google Vision AI (best accuracy, $1.50/1000 pages)
   - AWS Textract (good for forms/tables, $1.50/1000 pages)
   - Azure Document Intelligence (good for layouts, $1.50/1000 pages)

2. **Implement adapter**
   - Create `GoogleVisionOcrAdapter` or `TextractOcrAdapter`
   - Follow same `DocumentParserPort` interface
   - Add to `DocumentParserRouter` as fallback

3. **Test with scanned PDFs**
   - Parse "May - July 2026.pdf" (scanned financial report)
   - Parse "Brand Book 09_04_26 (1).pdf" (scanned brand guidelines)
   - Verify text extraction works

### Phase 5: Conflict Detection & Profile Compilation (1 day)

1. **Test conflict detection**
   - Feed same fact key from two sources with different values
   - Verify conflict created in `context_conflicts`
   - Verify onboarding question generated

2. **Test profile compilation**
   - Create approved profile version
   - Call compiler with `creative_brief` purpose
   - Verify only relevant sections returned
